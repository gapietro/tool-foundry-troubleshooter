# Mermaid Structural Comparator Pattern

A structural-deduplication technique for **Mermaid flowchart diagrams** generated by AI agents.
It parses diagram text into a graph of nodes and edges, then scores two diagrams with a
**weighted Jaccard** coefficient so structurally identical workflows are detected even when their
labels are worded differently. Use it to stop agent workflows from storing the same diagram twice.

> **Use this only when your agents emit Mermaid `flowchart` / `graph` text as a stored artifact.**
> If your agents describe processes in plain text, use the text-based techniques (Jaccard `#96`,
> TF-IDF `#97`) instead. If diagrams are stored only as rendered PNG/SVG images, there is nothing
> to parse — run TF-IDF over the description text.

## Overview

AI agents that document processes — Change Automation agents, Runbook Generators, architecture
documentation agents — often emit Mermaid flowcharts and persist them as Knowledge Articles,
attachments, or text fields on Change/Problem records. Two runs of the same agent frequently
produce the **same workflow** with **different wording**: `Approve Request` in one diagram,
`Request Approval` in the next. Raw text similarity on the Mermaid source misses this because the
strings differ; structural comparison catches it because the *shape of the graph* is the same.

The comparator runs entirely in scoped server-side script (Rhino, ES5-safe) with **zero external
dependencies**, so it is safe to call from a Business Rule, an AI Agent Script Tool, or a Scheduled
Job. It is the diagram-type counterpart to the text-based dedup utilities — plug it into the same
[three-tier dedup policy](#composition-with-the-three-tier-dedup-policy-98) in place of text
similarity whenever the artifact being compared is a diagram.

## Key Concepts

### Structural parse, not text match

`parseMermaidGraph(text)` turns a Mermaid string into two sets:

- **nodes** — the set of normalized node labels (lowercased, non-alphanumeric stripped, whitespace
  collapsed). `A[Approve Request]` and `B[approve request!]` both normalize to `approve request`.
- **edges** — the set of `"labelA->labelB"` strings built from `-->` arrows, resolved to the
  normalized labels of their endpoints.

It understands the `flowchart TB|TD|LR|RL|BT` and `graph` declarations (the declaration line is
skipped), arrow chains (`A --> B --> C` yields edges `A->B` and `B->C`), and standalone node
definitions (`A[Label]`). Normalization is what lets differently-worded-but-structurally-identical
diagrams score as duplicates.

> **Supported syntax subset.** The parser recognizes **solid `-->` arrows** and `A[Label]` node
> definitions only. It does **not** parse edge labels (`A -->|yes| B`), dotted/thick links
> (`-.->`, `==>`), or non-`[...]` node shapes (`(round)`, `{diamond}`) — those endpoints/edges are
> skipped, which lowers recall (a real duplicate may score below threshold). This is an acceptable
> trade-off for a duplicate *gate* (false negatives just mean a diagram is stored, not corrupted),
> but if your agents emit labeled or dotted edges heavily, lower the threshold or extend the parser.

### Weighted Jaccard: nodes 60%, edges 40%

`calculateStructuralOverlap(graph1, graph2)` combines two Jaccard coefficients:

```
overlap = 0.6 × jaccard(nodes₁, nodes₂) + 0.4 × jaccard(edges₁, edges₂)
```

where `jaccard(A, B) = |A ∩ B| / |A ∪ B|` (two empty sets are defined as identical → 1).

**Why nodes outweigh edges:** the set of *steps* in a process is a stronger identity signal than
the exact *wiring* between them. Two diagrams can document the same procedure while one adds a
retry loop or reorders a branch — the edges differ, but the nodes are the same. Weighting nodes at
60% keeps those recognized as duplicates without being so loose that genuinely different workflows
collide. Edges still matter (40%) so that two diagrams with the same vocabulary but a different flow
(e.g. an approval-first vs. approval-last process) are *not* falsely merged.

### Threshold guidance

The auto-suppress / review / store thresholds for the structural backend live in the **three-tier
dedup policy keystone** ([`similarity-dedup-policy-pattern.md`](similarity-dedup-policy-pattern.md),
#98), under the `mermaid-structural` row — this doc no longer restates them, so there is one source
of truth and the backend docs cannot drift. Those values (and all others) are labelled tunable
defaults imported from the external `merge-service.ts`, not ServiceNow constants.

`isDuplicateDiagram(...)` uses a single default threshold of **0.6** — the comparator's own boolean
"is this a duplicate at all" gate (a math-layer default, not a policy threshold). For the richer
auto-suppress / review / store decision, let the policy layer apply the `mermaid-structural` row off
the returned `{ score, backend: 'mermaid-structural' }`.

## Script Include: `MermaidStructuralComparator`

Golden example: [`sdk-examples/mermaid-structural-comparator.now.ts`](sdk-examples/mermaid-structural-comparator.now.ts)
→ implementation [`sdk-examples/server/MermaidStructuralComparator.js`](sdk-examples/server/MermaidStructuralComparator.js).

### Contract

| Method | Input | Returns |
|---|---|---|
| `parseMermaidGraph(mermaidText)` | Mermaid string | `{ nodes: {label:true}, edges: {"a->b":true} }` |
| `calculateStructuralOverlap(g1, g2)` | two parsed graphs | `Number` 0–1 (weighted Jaccard) |
| `isDuplicateDiagram(newText, existingTextArray, threshold)` | string, string[], number (default `0.6`) | `Boolean` |
| `compareDiagrams(textA, textB)` | two Mermaid strings | `Number` 0–1 (parse both, then overlap) |
| `findDuplicateIndex(newText, existingTextArray, threshold)` | string, string[], number | `Number` — index of first match, or `-1` |

> **Sets as plain objects.** The implementation represents node/edge sets as plain objects keyed by
> member string (not ES2015 `Set`), so it runs unchanged on Rhino in any scoped app. The Jaccard
> set math is **inlined** rather than calling `JaccardSimilarityUtil` (`#96`) so the Script Include
> is self-contained. If you have `JaccardSimilarityUtil` installed and want a single source of truth
> for set math, swap the private `_jaccard()` for a call into it — the public contract is unchanged.

### Example: detect a duplicate before storing

```javascript
var comparator = new MermaidStructuralComparator();

var existing = [
  'flowchart TD\n  A[Open Case] --> B[Triage] --> C[Resolve]',
  'flowchart TD\n  X[Create Change] --> Y[CAB Approval] --> Z[Implement]'
];

var incoming = 'flowchart TD\n  A[Open the case] --> B[Triage!] --> C[Resolve]';

var idx = comparator.findDuplicateIndex(incoming, existing, 0.8);
if (idx !== -1) {
  // Structurally identical to existing[idx] despite different wording — update it, don't insert.
  gs.info('Duplicate of diagram at index ' + idx);
}
```

### Example: AI Agent Script Tool wrapper

Pass `{text1, text2}` in, receive `{score, isDuplicate}` out — mirrors the I/O contract used by the
text-similarity utilities so the policy layer can treat all backends uniformly.

```javascript
(function execute(inputs, outputs) {
  var comparator = new MermaidStructuralComparator();
  var score = comparator.compareDiagrams(inputs.text1, inputs.text2);
  outputs.result = JSON.stringify({
    score: score,
    isDuplicate: score >= 0.6,
    backend: 'mermaid-structural'
  });
})(inputs, outputs);
```

## Storing Mermaid diagrams in ServiceNow for comparison

The comparator needs the **diagram source text**, so persist the Mermaid string itself — not just a
rendered image:

- **Text field on a record** — add a large-string / HTML-free field (e.g. `u_mermaid_source`) to the
  table that holds the artifact (KB article, Change, a custom `x_*_workflow_diagram` table). This is
  the simplest option and what the comparator reads directly.
- **Attachment** — if diagrams are stored as `.mmd`/`.txt` attachments, read the text via
  `GlideSysAttachment.getContent()` before comparing. Do not store only PNG/SVG renders — there is
  nothing to parse.
- **Per-run bucket** — tag each diagram with the generating run/session `sys_id` so the burst gate
  (below) can query just "the last N diagrams from this run" with an indexed `GlideRecord` query
  rather than scanning the whole corpus.

Build the `existingDiagrams` array by querying the stored source field; keep candidate sets small
(filter by type/session) to stay well inside platform transaction limits.

## Composition with the three-tier dedup policy (#98)

The comparator is the **math layer** for diagram artifacts. It slots into the calibrated
three-tier dedup policy ([`similarity-dedup-policy-pattern.md`](similarity-dedup-policy-pattern.md),
`#98`) exactly where text similarity would go — **the policy layer owns the tiers, the triggers, and
the thresholds; the comparator only answers "how structurally similar are these two diagrams"** and
returns `{ score, backend: 'mermaid-structural' }`. See the keystone for the full pipeline:

- **Burst gate** — a **before-insert Business Rule** that compares the new diagram against the last N
  in the same run bucket and calls `setAbortAction(true)` to suppress before write.
- **L3 auto-merge / L2 suggest** — an **after-insert Business Rule** (optionally handing off to a
  **Flow with a Created trigger, or a Subflow invoked by that flow/BR** — a Subflow is not triggered
  directly on record creation): at the auto-merge bar return the existing `sys_id` and discard the
  new record; in the suggest band write a Similarity Suggestion record for review.
- **Cross-type / corpus scan** — a **Scheduled Job on `sysauto_script`**, never inline, to stay under
  the ~298s synchronous-transaction cap.

The `mermaid-structural` threshold row (auto-merge / suggest bands) lives in the keystone, not here,
so the structural numbers cannot drift from the text backends. Tag results with
`backend: 'mermaid-structural'` so the policy selects the diagram row rather than the text rows. The
math layer and the policy layer stay separate concerns — the same way Jaccard (`#96`) and TF-IDF
(`#97`) feed that policy for text artifacts.

## Best Practices

1. **Verify the artifact is really Mermaid text.** Before adopting this, confirm your agents emit
   valid `flowchart`/`graph` syntax and store the source (not just rendered images). Otherwise use
   text similarity on the description.
2. **Keep candidate sets small.** Filter `existingDiagrams` by type and/or run `sys_id`. Single-pair
   and small-corpus comparisons are fine synchronously in a Business Rule; corpus-scale scans belong
   in a Scheduled Job.
3. **Tune the threshold to the agent.** Start at `0.6` for the duplicate gate and `0.8` for
   auto-suppress; raise if a chatty agent produces many near-duplicates that are intentionally
   distinct, lower if structurally identical diagrams slip through.
4. **Let the policy layer own the decision.** Call the comparator only for the score; keep
   suppress / merge / suggest logic in the policy tier so all backends behave consistently.

## Common Issues

| Issue | Cause | Solution |
|---|---|---|
| Everything scores 0 | Diagram text is empty or not a string, or stored as a rendered image | Confirm the source field holds Mermaid text; read attachment content before comparing |
| Distinct diagrams flagged as duplicates | Threshold too low, or diagrams share most step labels | Raise the threshold; remember edges are only 40% of the score |
| Real duplicates missed | Threshold too high, or labels normalize differently (numbers, IDs embedded in labels) | Lower the threshold; check that labels carry the same words after normalization |
| Slow / transaction timeout | Comparing against a large corpus inline | Move the scan to a Scheduled Job; shrink the candidate set with an indexed query |
